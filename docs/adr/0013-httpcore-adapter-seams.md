# 适配器编写模型:HttpCore 深模块 + 四接缝(新增交易所一律按此模式)

深化统一接口(架构评审候选 1):把 13 个适配器逐字重复的公共机制(`query_string` ×13、`public_get` ×12、`load_markets` 缓存 ×13、`value_decimal`/`parse_level` ×10 等)下沉为一个交易所无关的深模块 **HttpCore**(HTTP 请求骨架、市集缓存、客户端分页过滤、safe 提取、Precise 精确数值),统一接口面保持 158 方法枚举契约不变(ADR-0001 契约测试面不受影响);每个适配器只填四个接缝——**describe**(端点路径/参数)、**sign**(签名算法)、**handle_errors**(错误码映射)、**字段映射**(parse 覆写)。此切法完全对齐 ccxt 基类/子类模型(ccxt `base/exchange.py` 的 `fetch2`/`load_markets`/`safe_*`/分页全在基类,`describe()`/`sign()`/`handle_errors`/`parse_*` 留在子类),是经过 ccxt 93 家交易所验证的边界。形态采用混合:核心以**可选组合**为主(适配器持有 HttpCore 而非强制 trait 默认链),只对普适链(如"公共 GET → 解析")提供 trait 默认实现,不强制 REST 形状——未来纯 WS/GraphQL 交易所可直接跳过核心、不被 158 个默认实现束缚;预测市场特有逻辑(`OutcomeCtx` 解析、合成 ticker、RSA-PSS/secp256k1 签名)全部留在适配器侧,核心保持交易所无关。验收标准:ADR-0005 的"从 ccxt 转译批量补齐适配器"评估落地时,转译器只填四缝、零改动复用 HttpCore——能转译即证明兼容性。被否决:强制 trait 默认实现链(158 方法默认干活,接口/契约测试面失焦,REST 形状被强加于所有交易所)。**后续新增任何交易所(手写或转译)都必须按此模式,避免二次优化。**

- **Status**: accepted

**实施注记(2026-08-12,收口候选 2 — handle_errors 接缝)**:把一直只存在于文档的第四缝真正接线。新增 `httpcore::extract_exchange_error(body, exchange) -> Option<Error>`(ccxt 基类通用错误信封识别:Kraken `error[]`、Bybit `retCode`、HTX `status:"error"`、通用 `success:false` / `code` 数字 0/200 或字符串 `"0"`/`"200"`/`"200000"`/`"00000"` 为成功),并在 **`HttpCore::request_url` 单一漏斗**处调用——`request`/`public_get`/`request_ep`(95+ 转译适配器)全部经此,一次覆盖 100% 流量,无需逐个包裹器插桩。识别保守:仅对明确错误信号判定错误,绝不误伤成功响应(原行为是无错误信封的成功体静默交还解析层、错误体则抛晦涩 JSON 解析失败)。`HttpCore` 新增 `exchange: &'static str` 字段(构造处传入 id),错误上下文带 `[exchange=...]` 与 `[code=...]`;`HttpCore::new` 签名加第四个参数,14 处调用点(含 generic + 13 手写适配器)补齐 id。新增 12 个 mapper 单测,门禁全绿(构建/clippy -D warnings/fmt/test 57 lib + 5 fixture)。**已知遗留**:① 通用 mapper 统一映射为 `ErrorKind::Exchange`,各交易所「错误码→更细 ErrorKind(如 InsufficientFunds/OrderNotFound)」的精细分类是后续逐所覆写点(扩展 `extract_exchange_error` 按 id 分支或加 per-adapter 映射);② gate/coinbase 等错误信封为 `{label/message:...}` 且无 code 字段,通用 mapper 暂未覆盖,等同现状(不当误报);③ hyperliquid 绕开 HttpCore 直用 reqwest,不在此接缝覆盖(既有技术债)。

**实施注记(2026-08-12,架构评审报告候选 3 — Rust/Python 路由契约单一来源)**:消除 `key_matches` + 候选键列表在 `src/generic.rs`(Rust 引擎)与 `scripts/gen_adapters.py`(转译器)双份手工同步的静默漂移风险。两处确证漂移:Python `CANDIDATES` 字面量漏了 Rust `fetch_status` 路由所需的 `system_status` 与 `ping`(generic.rs:265),导致生成适配器对这些状态键永远路由不到。修复分两层:**(数据)** `scripts/gen_adapters.py` 删除手写 `CANDIDATES` 字面量,改为 `routing_candidates()` 在生成时直接解析 `src/generic.rs` 全部 `.find_first(&[...])` 候选数组(小写、去重)作为唯一来源,并加解析守卫(解析数 < 20 即失败,杜绝静默少发端点);`endpoint_relevant` 调用点零改动。**(算法)** `key_matches` 跨语言无法单一来源,故新增 `scripts/test_sync.py`(无 ccxt 依赖、可独立运行)用 `generic.rs::key_matches_word_boundary` 同一组 fixtures 做一致性守护,并检查 `routing_candidates()` 含全部必经候选键。该测试接入 `ci.yml` 新 job `transpiler-sync`(setup-python + `python3 scripts/test_sync.py`),漂移即让 CI 变红。验证:`python3 scripts/test_sync.py` 通过(37 keys + 8 fixtures);Rust 侧零改动,`cargo build/clippy -D warnings/fmt/test --all-features` 全绿。**注意**:此修复使生成器在「未来」生成时会包含 `system_status`/`ping` 端点(与引擎契约对齐,属正确行为),但已 check-in 的 95 个生成适配器是旧契约快照,需待候选 6(生成层漂移 / CI 重跑转译器)统一重生成方才物化——本候选不触发重生成(避免 95 文件噪声)。

**实施注记(2026-08-12,架构评审报告候选 4 — sign 接缝显式化)**:把一直隐式硬编码在 `generic.rs::sign_headers` 的默认签名(ccxt 基类 `HMAC-SHA256(method+url+body)` + `apiKey`/`sign`/`timestamp` 头)升级为 ADR-0013 第四缝 `sign` 的**结构化表达**。新增 `generic::SignScheme` 枚举(当前唯一变体 `HmacSha256Default` = 原 ccxt 基类默认),`GenericExchange` 增 `sign_scheme: SignScheme` 字段,`GenericExchange::new` 增第四参,`sign_headers` 改为按 `sign_scheme` 分派(当前唯一分支即原算法,行为零变化)。`impl_generated_adapter!` 宏扩为**可选三参**形式——两参形式显式默认到 `HmacSha256Default`(对应「默认 sign 显式」),故**已 check-in 的 95 生成适配器(两参)零改动即可编译**,无需重生成。转译器 emit 形式保持两参(默认即显式),未来若需按交易所定制签名(如 OKX/Binance/Bybit 的定制 HMAC 或 RSA-PSS),扩展此枚举 + 在 `sign_headers` 加分支 + 让转译器 emit 三参即可,且逐所定制签名本就属手写适配器职责(ADR-0013「预测/特殊市场逻辑留适配器侧」的同理)。验证:`cargo build/clippy -D warnings/fmt/test --all-features` 全绿(147 lib tests)。**边界**:ccxt 的签名是命令式(各所覆写 `sign` Python 方法),非声明式,故转译器无法从 `describe()` 推导非默认方案——这是生成适配器「只覆盖公开面 / 长尾」定位的固有边界,属预期。
